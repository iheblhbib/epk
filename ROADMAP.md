# Roadmap

This project is being built in 17 phases. Each phase is implemented to production quality before the next begins — the app is never built "blindly" in one giant pass.

## Phase 1 — Project Foundation ✅ (this pass)
Laravel 12 + MySQL backend, React + TypeScript + Vite + Tailwind frontend, full authentication (register/login/logout/forgot-password/reset-password/email-verification/change-password/profile), workspaces with `owner/admin/editor/viewer` roles enforced via Laravel Policies, dashboard shell with sidebar navigation, database foundation, API foundation, testing setup (Pest + Vitest).

## Phase 2 — EPK CRUD ✅
Create/edit/duplicate/delete/publish/unpublish an EPK, each tied to a workspace-scoped `Artist` (basic profile fields; full rich-text biography arrives with the builder in Phase 4). `artists` and `epks` tables (epks: uuid, workspace_id, artist_id, title, slug, status, cover_image, theme, custom_settings, SEO fields, published_at), Draft/Published/Archived statuses, policies (editor+ create/edit/duplicate/publish, admin+ delete), globally-unique slugs for the future public `/epk/{slug}` route. Preview and share are deferred to Phase 5 (Public EPK) and Phase 9 (Private Links), where they'll actually have something to point at.

## Phase 3 — Media Library ✅
Upload/multi-upload/drag-drop/preview/rename/delete/search/filter/sort/download for images (jpg/jpeg/png/webp), audio (mp3/wav/flac), video (mp4/mov), and documents (pdf/docx). Laravel Filesystem (`storage/app/public` + `storage:link`), secure random filenames (never the client's original name), content-based MIME whitelist (Laravel's `mimes` rule, not just extension/Content-Type) plus per-type size limits, so a renamed `.php` file is rejected regardless of its extension. Image thumbnails (WebP, via Intervention Image + GD) generated on upload with width/height captured in metadata.

## Phase 4 — EPK Builder ✅
Visual builder at `/epks/{epkId}/builder`: left sidebar (drag-and-drop section list via dnd-kit, enable/disable switch, duplicate/delete menu), center (live preview that reflects every edit instantly), right sidebar (section settings, plus a per-section title override). Desktop/tablet/mobile preview-width toggle. All 13 section types (Hero, Biography, Photos, Music, Releases, Videos, Press, Events, Social Networks, Contact, Downloads, Credits, Custom) are fully addable/reorderable/toggleable/duplicable now — Hero is a singleton, enforced both client- and server-side. Hero, Biography, Social Networks, Contact, Downloads, Credits, and Custom have complete settings editors (rich text via Tiptap, sanitized server-side with HTMLPurifier's `epk_richtext` profile so raw HTML never round-trips unfiltered); Photos/Music/Releases/Videos/Press/Events show a "coming soon" placeholder since their dedicated content entities (galleries, track uploads, streaming links) are scoped to Phase 7 — the section framework itself doesn't need to be rebuilt when that lands. Live preview and the settings-panel autosave share one mechanism: edits write straight into the TanStack Query cache (instant, no round trip) with the actual `PUT` debounced 500ms behind it.

## Phase 5 — Public EPK ✅
Public `/epk/{slug}` page, no auth required. A dedicated unauthenticated endpoint (`GET /api/public/epks/{slug}`) resolves the EPK server-side into public-safe output: media ids become real URLs (so the page never needs an authenticated media lookup), and Contact fields the artist toggled off (`show_phone`/`show_address`) are blanked before they ever leave the server — the frontend has no way to accidentally leak them. A non-published EPK (draft/archived) 404s exactly like an unknown slug, so the endpoint never confirms a press kit's existence before its owner publishes it. Renders enabled sections in position order with real per-type layouts (Hero banner, Biography/Custom rich text, Social Networks icon row, Contact with mailto/tel links, Downloads with file size + direct download links, Credits list); the six section types without dedicated content yet (Photos/Music/Releases/Videos/Press/Events, per Phase 7) simply render nothing rather than a builder-style placeholder. Sets `document.title` and a `meta[name=description]` tag from the EPK's SEO fields (falling back to the EPK title / artist bio) — genuine SEO crawling would need server-side rendering, which is out of scope here; this is the client-side half. The builder gained a "View public page" link (disabled with an explanatory tooltip until the EPK is published).

## Phase 6 — Themes & Customization ✅
5 original theme presets (Minimal, Dark, Editorial, Artist, Modern — each its own color palette, font pairing, button shape, radius, spacing, and header style) plus a "preset + overrides" customization layer: background/text/accent color, font, button style, radius, spacing, and header style can each be independently overridden, with `null`/absent meaning "inherit from the preset" — so switching presets never wipes a user's manual overrides. Resolution (`resolveTheme`) and CSS-variable mapping live in one shared, unit-tested module (`lib/epkThemes.ts`) consumed by both the builder's live preview and the public page, keeping `EPK data + Theme = Public EPK` a real equation rather than two independently-drifting renderers. The theme choice and every override are validated server-side (`EpkTheme` enum, per-field rules on `custom_settings`, unknown keys silently dropped) — never trusted from the client. A new "Theme" tab sits alongside "Section" in the builder's right panel: pick a preset from 5 live-swatched cards, then fine-tune any axis, with the same instant-cache-write-plus-debounced-save mechanism sections use. Editorial's serif option is a genuine self-hosted variable font (`@fontsource-variable/lora`), matching the no-external-font-CDN approach already used for the other three.

## Phase 7 — Music / Releases / Photos / Videos / Press ✅
Real content editors for the five section types that were placeholders since Phase 4 — implemented as richer JSON config shapes on the existing `EpkSection` (same architecture as Credits/Downloads/Social Networks) rather than five new database tables, since every section already supports add/reorder/duplicate/enable-disable and every item type is naturally scoped to one section instance. **Photos**: gallery with per-photo caption/credit, up/down reordering. **Music**: tracks with an HTML5 `<audio>` player, title falling back to the filename. **Releases**: album/EP/single with cover art and streaming links (Spotify, Apple Music, YouTube, SoundCloud, Deezer, Bandcamp). **Videos**: YouTube/Vimeo (server-side URL → embed-URL conversion, e.g. a normal watch link becomes an `/embed/` iframe URL) or a direct upload rendered in a `<video>` tag. **Press**: outlet/quote/article link/author/date. All five share the builder's existing settings-panel/live-preview/debounced-autosave machinery; the public-page resolver (`PublicSectionConfigResolver`) does the same job it already did for Hero/Downloads — turning bare media ids and raw URLs into ready-to-render URLs, dropping any entry whose referenced media was deleted or whose required field (title/outlet) is empty, so a stale reference degrades gracefully instead of rendering broken.

## Phase 8 — Analytics ✅
Internal analytics — genuinely no external service, not just "no third-party script tag": the public EPK page reports its own page views/downloads/plays to `POST /api/public/epks/{slug}/events`, which hashes the visitor's IP (HMAC with the app key, so it's never stored raw and can't be reversed) rather than geolocating it via an outbound API call. Country comes from whatever the hosting environment already provides — Apache's `mod_geoip2` (`GEOIP_COUNTRY_CODE`, common on cPanel) or a CDN's `CF-IPCountry` header — and is simply omitted, not guessed, when neither is present; the dashboard says so explicitly rather than showing fake data. Device/browser/OS come from `matomo/device-detector`, a local offline UA parser. `AnalyticsAggregator` turns raw events into totals (page views, unique visitors via `COUNT(DISTINCT visitor_hash)`, downloads, audio/video plays), a daily time series, and top-8 breakdowns (referrers, countries, devices, downloaded files) over a selectable date range. The dashboard (`/analytics`) is workspace-wide with an EPK picker and 7/30/90-day range buttons, rendered with Chart.js (installed since Phase 1, unused until now) for the page-views line chart plus proportional-bar breakdown cards. On the public page, video-play tracking covers direct uploads only — observing play state on a cross-origin YouTube/Vimeo iframe would require loading each platform's JS SDK, which this deliberately fast/SEO-focused page doesn't carry.

## Phase 9 — Private Links ✅
Password-protected, expirable, revocable private share links at `/private/{token}` — the main point being they work for a **draft** EPK too (unlike the public page, which requires `published`), so an operator can send a work-in-progress kit to a specific journalist or booker without publishing it. A high-entropy random token (`Str::random(40)`) is the only secret; an optional password is bcrypt-hashed, never stored plain. Unlike the public page's deliberate "everything 404s" secrecy, a private link tells the visitor *why* access ended — wrong password, or a distinct 410 for expired/revoked — since the token itself is already unguessable and know-it-or-you-don't, so that honesty isn't a meaningful leak. A correct password is remembered for the visitor's session (Sanctum's stateful-session cookie, no separate token scheme needed) so they aren't re-prompted on reload. Reuses the public page's entire section-rendering layer (extracted into a shared `sectionRenderers.tsx` used by both `/epk/{slug}` and `/private/{token}`) rather than a parallel implementation — the two pages differ only in how they fetch data and where they report analytics events. Per-link analytics extends Phase 8's existing `analytics_events` table with a nullable `private_link_id`, so the dashboard's "Top private links" breakdown is real usage data, not a separate bolt-on system; each link also keeps its own lightweight `view_count`/`last_viewed_at` for an at-a-glance number in the link management dialog (opened from the builder header) without needing to query analytics at all. Downloads-section files get a link-scoped download endpoint (`/private/{token}/downloads/{media}`) paralleling the public one, since the public download route intentionally only serves published EPKs.

## Phase 10 — Contacts ✅
Contact CRM scoped to the workspace (`contacts` table: name, email/phone/organization, category, notes, soft-deletes), 8 categories (journalist/radio/blog/label/booking/management/pr/other) via a backed enum, editor+ required to create/update/delete/import (any member can view). CSV export streams the workspace's contacts (`fputcsv`, chunked 200 at a time so it doesn't buffer the whole table in memory); CSV import is a native `fgetcsv` reader with header-driven column mapping (`name/email/phone/category/organization/notes`, in any order/subset) that deliberately refuses a positional fallback and reports an error if the header row has no recognizable `name` column, rather than silently importing garbage into the wrong fields. Contacts page: search (name/email/organization) + category filter, both enforced server-side via query params (not a client-side array filter), a table with inline edit/delete per row. Hit the same recurring Eloquent gotcha as three earlier phases — a column's DB-level `default(...)` isn't synced back into the in-memory model after `create()`, so `category` came back `null` instead of `'other'` in the immediate response until set explicitly in the create array (caught by a failing Pest test before it ever reached the browser).

## Phase 11 — Team & Permissions ✅
Closed the two real gaps left in Phase 1's already-functional Team page: invitations had no way to actually reach the invitee, and there was no workspace-level settings UI at all. Inviting a member now sends a `WorkspaceInvitationNotification` email (routed by address via `Notification::route('mail', ...)` so it works whether or not the invitee has an account yet) linking to `/invitations/{token}` on the frontend. That page previews the invite first (`GET /api/invitations/{token}`, deliberately public — the token itself is the access control, the same way a Slack/Notion-style invite link works) — "Jamie invited you to join Acme as Editor." Settings gained a "Workspace" tab: rename/description (owner+admin), and a danger zone for leave/delete (delete owner-only) wired to the workspace mutations Phase 1 already exposed but nothing in the UI called. Not new this phase: the not-ShouldQueue choice on the notification mirrors `VerifyEmail`/`ResetPassword` — this project's `QUEUE_CONNECTION=database` needs a worker process to ever deliver a queued job, so auth-adjacent emails all send synchronously instead of silently going nowhere on a dev box or a cPanel host with no worker running.

**Revised after user feedback** (the original version below routed an unauthenticated visitor through a separate `/login` or `/register` page and back, which was clunky enough to redo): the invitation page now handles sign-in inline, no bouncing anywhere. `GET /api/invitations/{token}` now also returns `has_account`; the page branches on it — an unauthenticated visitor sees either a plain password field (existing account) or a "create your account" mini-form (new account) right there, and two new atomic endpoints (`POST /invitations/{token}/login`, `POST /invitations/{token}/register`) log in-or-create-and-accept in one request each. The register path is where email verification gets skipped deliberately: clicking a link that only ever reached that address via email *is* proof of controlling it, so a second confirmation email would just re-check something already established. Chaining login-then-accept as two separate client-side mutations (the first version's approach for the "already has an account" case) turned out to have a real race: the login success handler updates the auth cache, which re-renders the page to a different branch before the second (accept) call's own success handler — including its redirect — reliably runs, intermittently leaving the invite technically accepted server-side but the visitor stranded looking at a stale "Accept invitation" button. One atomic backend call removes the race entirely; regression tests now cover both the wrong-password and the "account already exists" rejection paths for each.

## Phase 12 — Admin Panel ✅
Platform admin at `/admin`, gated end-to-end: an `EnsureUserIsAdmin` middleware (aliased `admin`) protects every `/api/admin/*` route, and a matching `AdminRoute` frontend guard (nested inside `ProtectedRoute`, so loading/auth/verified-email states are already handled) hides the whole section — including its sidebar link — from non-admins. `users.role` (from Phase 1) plus a new `suspended_at` column back it: admins can search/list every user, promote/revoke admin, and suspend/unsuspend (`LoginRequest::authenticate()` now rejects a suspended user's credentials outright, with a `assertGuest()`-verified test). Self-protection built in — an admin can't change their own admin/suspension status through this endpoint, closing off the easiest way to accidentally lock yourself out. Workspaces and EPKs get platform-wide list views (search, and status filter for EPKs) with a moderation action each: delete-any-workspace and force-unpublish-any-EPK. A genuinely new piece of infrastructure: an immutable `audit_logs` table + `AuditLogger` service, writing one row per moderation action (actor, action, subject, IP, timestamp) — scoped deliberately to admin-panel actions rather than retrofitted across the whole app, which is Phase 14 territory. "Subscriptions" from the original phase outline moves to Phase 13, which is what actually creates the billing schema it would show — showing subscription data before that table exists would mean building a fake view now and a real one later. "Media" and "analytics" are covered as aggregate stats (file count, total storage, page views) on the admin dashboard rather than a full cross-tenant media browser, which would need its own access-control design.

## Phase 13 — Billing Architecture ✅
A `subscriptions` table (one per workspace, auto-created — Free plan — the moment a workspace exists, via `Workspace::booted()`, so `PlanLimits` never special-cases "no subscription yet") carries `plan`/`status` plus `stripe_customer_id`/`stripe_subscription_id`/`current_period_ends_at` columns that sit unused until Stripe is actually wired in — a real data-backfill later, not a migration. The three tiers themselves (Free/Pro/Business — EPK count, storage, team members, custom themes, private links, white-label, custom domains) live in `config/plans.php` as static product data, not an admin-editable table, the same way Stripe's own Price/Product objects aren't edited from inside the app that sells them. A `PlanLimits` service resolves a workspace's effective limits and is the single enforcement point wired into five places: EPK creation (max count), theme customization (`custom_settings` overrides — every plan can still pick any of the 5 presets, only per-axis overrides are Pro+), private link creation, team invitations (max members), and media upload (storage cap, checked against incoming file size before the upload happens). Existing content on a downgraded/over-limit workspace is never revoked — the gates only block *new* creation, which is why the Free-tier demo workspace (seeded with 3 members against its 2-member limit) still works and simply can't add a 4th. Since Stripe checkout is out of scope, plan changes are admin-only for now (`PATCH /admin/workspaces/{workspace}/subscription`, audit-logged like every other admin action) — the honest state of things rather than a fake upgrade button; the real `/billing` page shows usage bars and the full plan comparison table but a non-current plan's card reads "Contact us to move this workspace to X" instead of pretending to charge a card that was never asked for.

## Phase 14 — Security & Performance ✅
A review pass rather than new features, so it's captured here as findings and fixes rather than a system description. **Rate limiting audit**: five sensitive endpoints had no throttle at all — `PUT /user/password` (6/min, matching the other auth-adjacent actions), the invitation preview/accept pair (20/min — the token is already a 64-char random unguessable secret, this is defense in depth against brute-forcing it), CSV contact import (10/min), and media upload (30/min, against storage/CPU abuse). **CSRF**: already fully handled by Sanctum's SPA cookie flow since Phase 1 — confirmed, no gap. **XSS**: audited every `dangerouslySetInnerHTML` in the frontend (3 call sites, all rendering rich-text HTML that's sanitized server-side through HTMLPurifier before it's ever stored — confirmed `RichTextSanitizer` is actually wired into `EpkSectionController`, not dead code) — no gap. **SQLi**: audited every `whereRaw`/`selectRaw`/`DB::raw` in the codebase — all either use fixed hardcoded column strings or parameterized bindings, no user input ever concatenated into SQL — no gap. **A real vulnerability found and fixed**: CSV/formula injection in contact export — a contact's name/organization/notes (free text, reachable via the add-contact form or CSV import) starting with `=`, `+`, `-`, or `@` would be evaluated as a live formula the moment the exported CSV opened in Excel or Sheets; every exported field is now guarded with a leading-quote escape when it starts with one of those characters, with a regression test proving the raw formula prefix never reaches the file. **Secure upload audit**: re-confirmed Phase 3's content-based (not extension-based) mime whitelist and per-type size caps, and confirmed there's no upload endpoint at all yet for the unused `avatar_path`/`logo_path` columns — nothing to harden there because there's no attack surface. **New**: a global `AddSecurityHeaders` middleware (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`) on every API response — HSTS deliberately excluded since that belongs at the TLS-termination layer set up in Phase 16, not hardcoded somewhere that would also ship it over a local plain-HTTP `php artisan serve`. **Caching**: the admin dashboard's platform-wide stats (several full-table COUNT/SUM scans) are now cached 60s via the file cache driver already configured for shared hosting — a minute of staleness costs nothing on a stats dashboard. **Query optimization**: added missing indexes on `audit_logs.created_at` and `audit_logs.action` (the admin audit log always sorts by the former and often filters by the latter); re-confirmed every list endpoint built across Phases 8–13 already eager-loads its relations rather than N+1ing.

## Phase 15 — Testing ✅
A gap-filling pass rather than a rewrite — every phase from 1 through 14 already shipped with its own tests (183 Pest tests, 37 Vitest tests going in), so this phase's job was finding what those feature-by-feature passes didn't cover, not duplicating them. Backend: `PlanLimits` had only ever been exercised indirectly through HTTP endpoints, which can't easily reach exact boundary conditions — a dedicated `Tests\Unit\Services\PlanLimitsTest` now asserts the free/unlimited-plan distinction and the "allowed at N-1, blocked at N" edges directly. `WorkspaceInvitationNotification`'s `toMail()` had never been rendered in a test at all (only that it got *sent*, via `Notification::fake()`) — a new test renders the actual mail body and asserts the workspace name, inviter, role, and frontend accept-link all land in it correctly, which is exactly the kind of thing that silently rots when a model relation gets renamed. Frontend: two of the newest pieces of routing/validation logic had zero coverage — `AdminRoute` (redirect-if-not-admin vs. render-if-admin, deliberately composed the same way `router.tsx` actually nests it under `ProtectedRoute` rather than in isolation, since it depends on that parent already having resolved the loading state) and `contactFormSchema` (email/category/length validation). Final tally: 189 backend tests (was 183), 45 frontend tests (was 37), all green.

## Phase 16 — cPanel Deployment Preparation ✅
[`docs/cpanel-deployment.md`](docs/cpanel-deployment.md) — the step-by-step guide `docs/architecture.md` promised back in Phase 1: prerequisites (PHP extensions, MySQL, subdomain setup), the full backend deploy (`composer install --no-dev`, `.env` values explained in a table, `migrate --force`, `storage:link`, `optimize`), the frontend deploy (build locally, upload `dist/`'s contents, why it needs no PHP-side setup at all), SSL via cPanel's AutoSSL, the redeploy process for both sides, a post-deploy verification checklist, and two real fallback paths — a no-SSH deploy (build `vendor/` locally, three ways to run one-time `artisan` commands without a shell) and the single-domain fallback the architecture doc already named but never detailed. One genuine gap found and fixed while writing it: **the frontend had no `.htaccess`** ([`frontend/public/.htaccess`](frontend/public/.htaccess), copied into every build by Vite) — without it, a direct visit or refresh on any client-side route (`/epks/5/builder`) 404s at the Apache level before React Router ever runs, since there's no real file at that path. Also verified `php artisan optimize` / `optimize:clear` actually run clean against this codebase end to end (config caching fails hard if `env()` ever leaks outside a config file, so this is a real check, not a formality) and confirmed there's honestly nothing to hang `schedule:run` on yet — no `Schedule::` entries, no queued jobs anywhere in the app (every notification sends synchronously on purpose, see Phase 11) — documented as such rather than inventing a placeholder task; the cron entry itself is still worth setting up now since it's inert and free.
